# @synthlet/polyblep-oscillator

> A band-limited virtual-analog oscillator, as an AudioWorklet

Part of [Synthlet](https://github.com/danigb/synthlet) —
[docs and a live demo](https://danigb.github.io/synthlet/docs/polyblep)

Four band-limited waveforms — sine, triangle, sawtooth, square — generated by one
discontinuity scheduler: every waveform is a naive function of the phase plus a
list of where its edges and corners fall, and each of those gets a polynomial
band-limiting correction written into the samples around it.

It does five things `OscillatorNode` cannot:

- **pulse-width modulation** on the square, at audio rate
- **a continuous triangle→saw morph**, the same parameter
- **hard sync**, sub-sample accurate and band-limited, triangle included
- **through-zero linear FM** — `frequency` is bipolar and the phase runs backwards
- **an initial phase**, per instance, so stacked oscillators stop combing

Every parameter but `type` is a real a-rate `AudioParam`, so all of it can be
driven by another node at audio rate.

## Install

```bash
npm i @synthlet/polyblep-oscillator
```

Or `npm i synthlet` for every module, from which the same names are exported.

## Usage

```ts
import {
  PolyblepOscillator,
  PolyblepOscillatorType,
  registerPolyblepOscillatorWorklet,
} from "@synthlet/polyblep-oscillator";

const ac = new AudioContext();
await registerPolyblepOscillatorWorklet(ac);

const osc = PolyblepOscillator(ac, {
  type: PolyblepOscillatorType.Square,
  frequency: 220,
  width: 0.25, // a 25% pulse
});
osc.connect(ac.destination);

// ...when you're done with it
osc.dispose();
```

Registration is asynchronous and has to happen before you create anything: an
`AudioWorkletProcessor` cannot fetch its own code, so it must be installed on the
context first. Everything after that is synchronous.

There is no `start()`. The oscillator runs from the moment it exists; gate it with
an amplifier, the way a modular oscillator is gated.

## Parameters

| Param       | Default        | Min    | Max   | Rate   | Meaning                                         |
| ----------- | -------------- | ------ | ----- | ------ | ----------------------------------------------- |
| `type`      | 2 (`Sawtooth`) | 0      | 3     | k-rate | Waveform, in brightness order                   |
| `frequency` | 440            | −20000 | 20000 | a-rate | Hz. **Bipolar** — negative runs the phase back  |
| `detune`    | 0              | −1200  | 1200  | a-rate | Cents, ±1 octave. Multiplies `frequency`        |
| `width`     | 0.5            | 0      | 1     | a-rate | Pulse width on the square, peak on the triangle |
| `sync`      | 0              | 0      | 1     | a-rate | Hard sync. A **rising edge** resets the phase   |

All five are real `AudioParam`s — settable, schedulable, and patchable from
another node. The same list is available at runtime as
`PolyblepOscillator.descriptors`, if you are generating UI from it.

One more input is **not** an `AudioParam`:

| Option  | Default | Accepts              | Meaning                                                         |
| ------- | ------- | -------------------- | --------------------------------------------------------------- |
| `phase` | 0       | `number \| "random"` | The initial phase in `[0, 1)`, and where a `sync` edge restarts |

It is a construction option because it is a one-time initial condition; an
`AudioParam` would imply it meant something continuously. A number is taken
modulo 1, so `1.25` and `-0.75` both mean `0.25`.

```ts
const voices = [-7, 0, 7].map((detune) =>
  PolyblepOscillator(ac, { frequency: 220, detune, phase: "random" }),
);
```

`"random"` draws once per instance, which is what stops three detuned oscillators
starting phase-locked and combing through the attack — the part of a supersaw you
actually hear.

## Waveforms and phase

`type` selects a waveform, in brightness order:

| `PolyblepOscillatorType` | value       | naive shape                                 |
| ------------------------ | ----------- | ------------------------------------------- |
| `Sine`                   | 0           | `sin(2π · phase)`                           |
| `Triangle`               | 1           | minimum at phase 0, maximum at half a cycle |
| `Sawtooth`               | 2 (default) | `2 · phase − 1`                             |
| `Square`                 | 3           | `+1` for the first half of the cycle        |

**Phase 0 is the step for the sawtooth and the square, and the triangle's
minimum.** That is the convention the whole package is built on rather than an
accident of the implementation: it is what lets one `width` parameter mean pulse
width on the square and peak position on the triangle, because in both families
the second discontinuity sits at `width`.

The square is `+1` until `width`, matching the Web Audio spec's
`OscillatorNode`. It used to be `-1`, so a patch that mixes this oscillator with
a native one, or that feeds a rectifier or a wave shaper, will sound different.

`frequency`, `detune`, `width` and `sync` are **a-rate**, so all four take an
audio-rate signal and are read per sample. `type` is k-rate; changing it
mid-note is band-limited like any other discontinuity, so it does not click.

## Width

`width` (0…1, default 0.5) means two related things, and the sine and the
sawtooth ignore both:

| `type`     | `width` is        | at 0.5               | towards 0 / 1                     |
| ---------- | ----------------- | -------------------- | --------------------------------- |
| `Triangle` | the peak position | a symmetric triangle | a rising or falling ramp          |
| `Square`   | the pulse width   | a square wave        | a narrow pulse of either polarity |

There is no separate "skewed sawtooth": it is the triangle at `width → 1`, so
the morph is already reachable and a second spelling would only be another
branch.

**A pulse wave has a real DC component of `2 · width − 1`.** That is correct
behaviour and not something to filter out — a 10% pulse sits at −0.8 and swings
to +1, which is what makes pulse-width modulation move the way it does. If a
patch needs it removed, remove it downstream.

The DSP clamps `width` to `[2·|increment|, 1 − 2·|increment|]` every sample, so
it never quite reaches 0 or 1. Two samples is the band-limiting kernel's
support, and closer than that the two discontinuities' corrections overlap; on
the triangle the same bound is what keeps the corner finite as the short ramp
gets short. The declared range is still `0…1`, because that is the range a UI
slider should offer, and the DSP is total across it. In practice the clamp only
bites in the top octaves: at 440 Hz it allows a 2% pulse, at 4 kHz an 18% one.

## Frequency, and through-zero FM

`frequency` is **bipolar**, `-20000…20000` Hz. Two consequences worth knowing:

- **`frequency = 0` holds.** The phase freezes and the output holds a finite
  constant. It is not an error and it is not silence — and it is a value you will
  hit whether you mean to or not, because connecting a node to an `AudioParam`
  writes `0` into it first.
- **A negative frequency runs the phase backwards**, and it is band-limited going
  that way: the sawtooth and the square hold the same alias floors at `−f` as at
  `+f`, to the decimal.

An `AudioParam` **sums** its inputs with its intrinsic value, so connecting a node
to `frequency` is _linear_ FM by construction:

```ts
const carrier = PolyblepOscillator(ac);
const modulator = PolyblepOscillator(ac, { frequency: 110 });
const depth = new GainNode(ac, { gain: 800 }); // FM depth, in Hz

modulator.connect(depth).connect(carrier.frequency);
carrier.frequency.value = 440; // the connection zeroed it; put the pitch back
```

With a depth of 800 Hz against a 440 Hz carrier, the sum spends part of every
cycle below zero. That is the point: the phase reverses instead of clamping flat.
A modulator that is half-wave rectified at the bottom is a _different_ modulator,
so clamping does not tame the sound, it produces the wrong spectrum.

Use `detune` for vibrato instead — it is in cents, so it is musically
proportional, and it multiplies `frequency` rather than adding to it.

## Hard sync

A **rising edge** on `sync` — the transition from non-positive to positive,
synthlet's one gate contract — restarts the phase at `phase`. The reset is
scheduled as a step _and_ a slope change at the interpolated crossing instant
rather than spliced at the sample boundary, so it is band-limited for all four
waveforms, the triangle included.

```ts
const master = PolyblepOscillator(ac, { frequency: 110 });
const slave = PolyblepOscillator(ac, { frequency: 660, sync: master });
```

That is the classic sound: the master's pitch sets the note you hear, the slave's
`frequency` sweeps the timbre.

Three rules, all from the gate contract:

- Holding `sync` positive fires **once**, not once per sample. A falling edge
  fires nothing.
- A one-shot reset is `osc.sync.setValueAtTime(1, t)` followed by
  `setValueAtTime(0, t + eps)`.
- **Never drive it with `setTargetAtTime`.** A signal that asymptotes towards zero
  never reaches it, so the gate would never re-arm.

## Latency

The output is delayed by **two samples**, about 45 µs at 44.1 kHz. It is the
only latency in synthlet, and it is deliberate.

The band-limiting correction spans ±2 samples around a discontinuity, so it has
to be written into samples that have already been computed. The alternative is
to predict where the discontinuity will land from the increment at the moment it
is detected — which is what the package used to do, and what places the
correction slightly wrong as soon as the frequency is moving quickly. Buying two
samples of delay buys correct placement under audio-rate FM, and it is constant,
so it never smears.

## Measured quality

Alias SNR in dB at a 44.1 kHz sample rate, higher is better:

| waveform | 440 Hz | 1 kHz | 2 kHz | 4 kHz | 8 kHz |
| -------- | ------ | ----- | ----- | ----- | ----- |
| sawtooth | 45.5   | 42.3  | 40.1  | 34.5  | 26.8  |
| square   | 46.8   | 43.2  | 45.1  | 43.8  | 26.6  |
| triangle | 80.7   | 70.2  | 67.0  | 60.6  | 36.2  |

The metric: a 32768-point FFT of a Blackman-Harris-windowed render, with energy
within ±10 bins of each harmonic counted as signal and everything else as noise.

**These figures are this repository's own metric, and they are comparable only
within it.** It is not any published paper's definition, so reading them against
figures from the literature is not meaningful. What they are good for is
comparing one implementation here against another, which is what they were built
for.

Every number above is asserted by `src/dsp.test.ts`, as a one-sided floor at the
measured value minus 1.5 dB — a waveform that gets better needs no edit, one that
gets worse fails the build. The triangle carries three more frequencies there
(67.2 / 63.7 / 76.4 dB at 1661 / 4186 / 7040 Hz); its 8 kHz figure is low because
its third harmonic folds above 7350 Hz.

The **sine** has no discontinuity, so there is nothing to correct and no alias
floor to quote: what the metric reads for it is the `Float32Array`'s own
quantisation noise. The tests hold it above a flat 90 dB as a regression net.

A band-limited waveform does not peak at 1.0 — the harmonics above Nyquist are
gone, so the ones that remain no longer add up to the corner. The **triangle**
peaks at 0.999 / 0.998 / 0.995 at 20 / 55 / 110 Hz, which `src/dsp.test.ts` also
asserts.

**There is no number here for the comparison against `OscillatorNode`**, and that
is on purpose: nobody has measured the native node with this metric, and an
unmeasured dB figure in a README is exactly the kind of claim this package's
documentation exists to avoid. The
[docs page](https://danigb.github.io/synthlet/docs/polyblep) runs both at the same
pitch with a spectrum analyser on each — sweep into the top two octaves and judge
it yourself.

and BLAMP polynomials by integrating the centred cardinal B-spline once and twice,
from the spline's own definition, and `src/blep.test.ts` asserts the three
properties that characterise them. No coefficient table was copied out of any
paper, so the credits above are intellectual, not the provenance of code. Brandt
2001 in particular contains no polynomial at all — it is cited for hard sync.
